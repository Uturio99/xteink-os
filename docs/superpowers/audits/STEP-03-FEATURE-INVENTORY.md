## STEP 03C — Blocker disposition

**Scope and decision authority.** SOURCE-INSPECTED at the baseline and SDK pin above. This section supersedes the three STEP 03B blocker calls. Acceptance here means the parity inventory describes what the baseline offers. The PO retains authority over changes to user behavior.

### 1. Boot without a mountable SD card — ACCEPTED BASELINE LIMITATION

Setup samples the recovery chord before mounting storage. X4 Pro uses Power-button wake with Down held. `Storage.begin()` delegates to the SDK card manager. The X4 Pro profile uses native SDMMC, where device initialization or volume mount can fail. On failure setup initializes the display, requests “SD card error” and returns before panic processing, saved state, Home or the recovery picker. The message activity draws on entry and supplies no local retry or insertion handler. This describes the setup return, not a processor halt. Evidence: `src/main.cpp:616-644,790-796`, `lib/hal/HalStorage.cpp:36`, `freeink-sdk/libs/hardware/BoardConfig/include/BoardConfig.h:1950-1955`, `freeink-sdk/libs/hardware/SDCardManager/src/SDCardManager.cpp:23-79`, `src/activities/util/FullScreenMessageActivity.h:10-24`, `src/activities/util/FullScreenMessageActivity.cpp:7-16`.

**User impact and decision.** A user needs a mountable card on a subsequent boot to reach SD recovery. Once reached, cancelling or acknowledging a failed image in recovery returns to the picker. The mount prerequisite predates XTEInk. A regression would be losing the picker with a working card and the recovery chord, or hiding the error when mounting fails. Preserve both branches. Inventory closure needs no separate PO exception. Any request for cardless recovery needs separate PO scope. **DEFERRED** to recovery QA: observe the error on an absent or unreadable card, then check picker entry and cancellation on a fresh boot with a readable card.
